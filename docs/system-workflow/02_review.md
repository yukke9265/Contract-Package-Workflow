# システム開発全体のワークフロー検討 — ドラフトレビュー

> **ステータス**: レビュー記録  
> **対象**: [01_draft.md](01_draft.md)

---

## レビュー方針

ドラフトに対して以下の観点でレビューを行う。

1. 各候補の説明が具体的かつ実用的か
2. メリット・デメリットに漏れや偏りがないか
3. 現行の契約パッケージワークフローとの整合性
4. 実際のプロジェクトへの適用可能性
5. ドキュメントの構成・可読性

---

## 候補 A（逐次統合型）に対するレビュー

### 良い点

- 「前のモジュールが完成してから次へ進む」という制約が、契約の安定性を担保している点は現行ワークフローの思想と一致している
- 小規模チームには実際に適している

### 改善点・指摘事項

1. **システム契約（上位契約）の具体化が不足**: 「全体 API・境界の定義」とあるが、システム契約パッケージがどのような構造を持つか、現行テンプレートとどう違うかが不明瞭。システム契約テンプレートを定義する必要がある。

2. **逐次開発における依存方向の制約**: モジュール間に循環依存が生まれた場合の対処が述べられていない。依存関係を有向非循環グラフ（DAG）として設計する制約を明示すべき。

3. **ブロッキングリスクの軽減策の欠如**: デメリットとして「1 モジュールのブロックがシステム全体を止める」と挙げているが、対処法（スタブ・モック契約の活用など）が示されていない。

4. **統合テストの定義**: 「統合テスト」と書かれているが、それが契約パッケージワークフロー内でどう位置づけられるか（新たな契約パッケージとして扱うのか、など）が不明。

---

## 候補 B（並列開発型）に対するレビュー

### 良い点

- モジュール間契約パッケージ（Interface Contract Package）という概念を明示した点は有用。現行ワークフローを自然に拡張している
- 並列化のメリットが現実的な規模感で述べられている

### 改善点・指摘事項

1. **モジュール間契約パッケージの作成プロセスが未定義**: 「先に凍結する」とあるが、誰が・どのタイミングで・どのツールを使って作るかのフローが欠けている。候補 B 固有のワークフロー図（上位設計 → IPC 作成 → 並列実装）を詳しく示すべき。

2. **モック実装の活用**: 並列開発中に他モジュールの実装が存在しない段階でのテスト方法が述べられていない。モジュール間契約パッケージからモックを自動生成する仕組みを検討すべき。

3. **統合フェーズの遅さ**: 「全モジュール完成まで統合テストができない」とあるが、インクリメンタル統合（完成したモジュールから順次統合していく）の可能性を検討すべき。

4. **コンフリクト解決**: 並列開発時の共通コード（共有ヘッダ、ユーティリティ）の扱い方が不明。共通部分も契約パッケージとして分離する指針を示すべき。

## 候補 C（マルチリポジトリ型）に対するレビュー

### 良い点

- バージョン管理と再利用性に関する説明が具体的
- 大規模組織に向いている理由が明確

### 改善点・指摘事項

1. **契約パッケージのリリース管理が未定義**: 「リリース済み契約パッケージを消費する」とあるが、契約パッケージをどのようにパッケージング・公開するか（ヘッダのみ、CMake Find モジュール、パッケージマネージャー経由など）が不明。

2. **ツールチェーンの要件**: マルチリポジトリ管理には repo ツール、git submodule、CMake FetchContent など複数の選択肢があり、それぞれトレードオフが異なる。ツール選択の指針を示すべき。

3. **統合リポジトリの運用**: 統合リポジトリが肥大化した場合の分割戦略、統合テストの実行頻度と責任者が不明確。

4. **初期コストの具体化**: 「初期コストが高い」とあるが、何を用意する必要があるかのチェックリストがあると実践的。

## 候補 D（フィーチャー駆動型）に対するレビュー

### 良い点

- ユーザー価値との整合を重視する観点は、プロダクト開発においてとても重要
- フィーチャー契約という概念が、要件追跡の観点で有用

### 改善点・指摘事項

1. **フィーチャー契約の形式が未定義**: 現行の契約パッケージテンプレートはモジュール（クラス）レベルのものだが、フィーチャーレベルの契約はどのような形式を取るのか。ユーザーストーリー、受け入れ基準、API 境界の記述フォーマットを定義する必要がある。

2. **フィーチャーとモジュールの二重管理**: フィーチャー契約と実装契約パッケージの両方を維持すると、二重管理の負荷が生まれる。どちらを正本とするか、どう同期するかを明確にすべき。

3. **フィーチャー完了の定義**: フィーチャー契約ベースの受け入れ条件（ユーザー視点）と、モジュール契約ベースの受け入れ条件（技術視点）の関係が不明瞭。

4. **既存ワークフローとの整合**: 現行の `ContractPackage_Template` や `Validate-ContractPackage.ps1` をフィーチャー駆動型にどう適用するかの説明が必要。

---

## 比較表に対するレビュー

### 良い点

- 観点ごとの比較が一覧で見やすい

### 改善点・指摘事項

1. **定性評価の根拠**: 「低・中・高」の評価根拠が示されていない。評価基準を定義するか、簡単な説明を付記すべき。

2. **ハイブリッドの可能性**: 現実のプロジェクトでは、「小規模なら A、大規模なら C」という二択ではなく、たとえば「A で始めて C に段階移行する」「B と D を組み合わせる」などのハイブリッドアプローチが現実的。この観点を追加すべき。

3. **契約パッケージワークフローとの親和性**: 各候補が現行ツール（`New-ContractPackage.ps1`、`Validate-ContractPackage.ps1`、`Invoke-CMakePreset.ps1`）をどの程度そのまま活用できるかを評価項目に加えるべき。

## 全体への共通コメント

1. **システム設計フェーズの欠如**: どの候補も「システム全体の初期設計（アーキテクチャ決定）」フェーズと契約パッケージワークフローの接続が薄い。アーキテクチャ決定記録（ADR）との連携や、アーキテクチャ設計が契約作成の前提になる流れを示すべき。

2. **変更管理**: システムが動き始めた後の変更管理（モジュール間契約の改訂、後方互換性の維持など）がどの候補にも述べられていない。

3. **AI エージェントの役割拡張**: 現行ワークフローでは AI エージェントの役割がモジュール単体に閉じているが、システムレベルでは「複数モジュールの整合性確認」「システム契約からの自動分解」などの新しい役割が考えられる。

4. **実例の欠如**: 各候補を具体的なシステム例（例：HTTPサーバー、データパイプラインなど）に当てはめた記述がなく、読者がイメージしにくい。
